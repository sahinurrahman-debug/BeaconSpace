# Flood damage from space — Multimodal AI Hackathon 2026, Track B

> *When roads, bridges and phone lines are gone, rescuers still need to know where the damage is and who is cut off.*

Give the system **an area and a flood date**. From free satellite data only, it answers three questions:

| Question | How |
|---|---|
| **Where did the flood hit?** | Sentinel-1 radar change detection (same orbit track, ~12 days apart) + a trained U-Net, gated by Copernicus-DEM terrain (slope, height-above-nearest-drainage); Sentinel-2 adds water evidence where the sky is clear. |
| **What was damaged?** | Pre-event OpenStreetMap buildings, roads and bridges overlaid on the flood/debris footprint → *likely destroyed / affected / exposed*. |
| **Who is cut off?** | Road graph before vs. after; settlements whose route to the nearest hospital/town is gone (or much longer), with the blocked segment located. |
| *Bonus* | Click an upstream point → D8 flow path down the valley + settlements in the susceptible corridor. |

Outputs: an interactive **map dashboard**, a **one-page bilingual (English / नेपाली) situation report** (every number is read from the
system's own maps — nothing is generated by a language model), GeoTIFF/GeoJSON products and a `provenance.json` that proves which
inputs were used.

*Educational prototype — not an operational tool. Contains no images of victims.*

## 1. Run it (5 minutes + data download)

```bash
git clone <this repo> && cd <this repo>
python -m venv .venv && . .venv/bin/activate          # Windows: .venv\Scripts\activate
pip install -r requirements.txt                       # Python 3.10 – 3.14
```

**No account or API key is needed**: Sentinel-1 (Microsoft Planetary Computer RTC), Sentinel-2 (AWS Earth Search), Copernicus DEM
(AWS) and OpenStreetMap history are all open endpoints.

### Dashboard (recommended)

```bash
streamlit run app/dashboard.py
```
Sidebar → *Run a new analysis* → choose the **Trishuli** preset (or type any bounding box + flood date) → **Run analysis**.
Finished runs are listed under *Open a finished run*.

### Command line (same engine)

```bash
python -m floodsys run --preset trishuli                                  # case study (≈ 2 500 km²)
python -m floodsys run --bbox 85.30 28.10 85.45 28.25 --event 2026-08-26  # any area / date
python -m floodsys run --preset trishuli --res 10 --pairs 3               # sharper, slower
python -m floodsys run --bbox ... --event ... --trace 85.38 28.22         # + flow-path bonus
```
Results are written to `outputs/<run>/`: `sitrep.pdf|html`, `map.png`, `dashboard_map.html`, `summary.json`, `classes.tif`,
`impact_polygons.geojson`, `buildings_affected.geojson`, `roads_hit.geojson`, `settlements.geojson`, `blocked_segments.geojson`,
`flowpath*.geojson`, `provenance.json`.

### Tests


## 2. How it works

```
 area + flood date
      │
      ├─► Sentinel-1 RTC (Planetary Computer) ── plan same-track pairs ─► pre (mean of ≤2) / post ─► dB, Lee filter
      ├─► Copernicus DEM ───────────────────────► slope, HAND, D8 flow directions
      ├─► Sentinel-2 L2A (cloud mask by SCL) ────► MNDWI water evidence where clear
      │
      ▼
 detect:  AI U-Net (7 ch) or physics rule  →  flood water │ debris/scour │ permanent water
          terrain gating, hysteresis change detection, valley-connectivity filter, multi-track union + agreement
      │
      ├─► OSM snapshot before the event (ohsome → Overpass `[date:]` → local file)
      │       buildings ─► destroyed_likely / affected / exposed        roads, bridges ─► km hit
      │       road graph pre vs post ─► cut_off / longer_route / connected (+ where the road is cut)
      └─► situation report (EN + NE) · dashboard · GeoJSON/GeoTIFF · provenance
```

Key design choices (details in the report):

* **Same-track pairs only.** `plan_pairs` groups acquisitions by relative orbit and never mixes tracks pixel-by-pixel. It prefers the first post-event pass, a pre-image ≈ 12 days earlier and full AOI coverage; for the case study it chose RO 85 (16 → 28 Aug) and RO 19 (24 Aug → 5 Sep).
* **Radar shadow can't fool it.** Water must be dark *and* have dropped ≥ 3 dB relative to the pre-event image; slope and HAND gates remove steep or high ground.
* **Debris** (mud, boulders, scoured channel) raises or changes backscatter in both polarisations: a speckle-robust smoothed log-ratio with hysteresis thresholds derived from the *empirical noise of stable hillslopes* (not from reference maps).
* **Optical never vetoes radar**; clear-sky Sentinel-2 water adds flood-water evidence and raises confidence.
* **Honest confidence**: `support.tif` counts agreeing orbit tracks per pixel.

### AI component
*Flood segmentation model* (Track B option 1): U-Net/ResNet-34, 7 input channels, trained on **Kuro Siwo** (Bountos et al., NeurIPS 2024) pre/post SAR pairs, 3 classes (no water / permanent water / new flood). Evaluated on Kuro Siwo's held-out test events (different geographies), on a mountainous subset, against a physics baseline, with a false-alarm test on flood-free patches, and — for Himalayan terrain — on the EMSR927 case study and on **null-event pairs** (`scripts/null_test.py`). See `docs/` and the report for numbers.

## 3. Data rules — how compliance is enforced

| Rule | Implementation |
|---|---|
| Allowed inputs only: Sentinel-1/2, Copernicus DEM, OSM *before* the event, training datasets | `floodsys/data/*`; `provenance.json` lists every source and field `forbidden_inputs_used: []` |
| **No** Copernicus EMS / UNOSAT / other damage maps as input; **no** post-event OSM edits | EMS reference is only read by `scripts/evaluate_emsr927.py` (outputs vs. reference). OSM is requested with a date `< event` (`RunConfig.snapshot` is rejected otherwise); the Overpass fallback uses date-pinned *attic* queries, never the live database. |
| Runs end-to-end from raw satellite data for any area/date | `python -m floodsys run --bbox … --event …` (raw COG reads, nothing pre-baked) |
| Thresholds not tuned on EMSR927 | Parameters (`floodsys/config.py`) set from SAR physics + stable-terrain noise statistics + null-event pairs, and frozen **before** the EMSR927 comparison |

### OpenStreetMap provider chain
1. **ohsome API** `elements/geometry` (the provider named in the brief).
2. **Overpass** `[date:"<snapshot>"]` attic queries (`overpass-api.de`). This is slow on the public server, so tiles are cached on disk and the fetch is resumable (`python scripts/prefetch_osm.py --preset trishuli`). *On the development network the public ohsome geometry endpoint answered HTTP 403, which is why the fallback exists.*
3. A local file per layer in `data/osm_snapshot/{roads,buildings,places,health}.gpkg` (must predate the event).

A pre-fetched cache for the case study can be shipped in `cache/osm/` (ODbL — keep the attribution).

## 5. Limitations (short list — full section in the report)
* Sentinel satellites revisit every few days: this maps the scene **at the post-event pass**, it cannot warn of a glacier collapse minutes ahead, and flood extent may have changed since.
* 10–20 m pixels: single houses, small bridges and narrow roads are inferred from overlap with the footprint, not seen directly.
* "Debris" is detected as *change*; the system cannot say whether it is mud, boulders or a landslide, nor its depth.
* Monsoon cloud limits optics (≈ 27 % clear on 27 Aug in the corridor); radar sees through cloud but is confused by wet snow and steep-slope geometry.
* Cut-off analysis uses *mapped* roads (OSM before the event): unmapped tracks, footpaths, helicopter access or repairs done since are unknown; routes leaving the analysed area are assumed intact.
* The trained model saw mostly low-relief floods and no debris-flow labels.
* Nepali text is template-based and needs review by a native speaker.
